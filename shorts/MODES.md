# ５種類のショート動画・制作プリセット

この文書は、このフォーク用の制作判断です。再生数を実証した攻略法ではありません。指定の型を１つ選び、その節だけを読むのを基本にします。[共通検品](QUALITY.md)は全形式で必須です。参照先の詳細は[出典と採否](SOURCES.md)にあります。

<a id="text-tsukkomi"></a>
## 1. 文字ツッコミ型 — `text-tsukkomi`

**選ぶとき：** 架空悪口図鑑、あるある、皮肉、短文エッセー。説明文を面白く読ませたいときの第一候補。

**読む資料：** この節 → [ohneis-style](../references/ohneis-style.md)の文字階層・強調・画面の種類。補助として `kinetic-typography` のRemotion向け部分だけ。

**組み立て：** 状況が分かる一言 → 本人の理屈 → 行動との食い違い → ツッコミ。長い人物紹介から始めない。１本に１つの中心的な笑いを選び、原稿の全項目を無理に詰め込まない。省略箇所は制作メモに残す。

**画面：** 発言・補足・ツッコミを別のテキストレイヤーにする。補足を小さく、笑いの核だけ大きくする。ただし小さい補足も読めるサイズを保つ。同じカードを切り替えるだけにせず、発言画面／対比画面／オチ画面を必要に応じて使う。

**動きと間：** 状況説明は落ち着いて出す。オチは前の内容を読めてから出す。全文の常時揺れ・全文タイプライター・全画面ズームの連発はしない。「毎回違う動き」より意味の一貫性を優先する。

**使わない：** 購入誘導の定型、商品解決の押し込み、強制的な説教オチ、英語の小文字統一・セリフ体指定の日本語への直輸入。音声がなければ音声単語タイムスタンプ前提の設計は採用しない。

**検品：** 無音で状況とオチが伝わるか。読む前に次の文章が出ないか。原稿にない出来事を原文の事実として扱っていないか。架空人物であると分かるか。

**依頼例：**「この原稿を文字ツッコミ型で。基本は無音、最後は説教ではなく元のネタの矛盾で落として。」

<a id="chat-story"></a>
## 2. 会話型 — `chat-story`

**選ぶとき：** 返信の意外さ、すれ違い、言い訳、夫婦・友達・職場の架空会話。長い説明より数往復の会話で成立するとき。

**読む資料：** この節 → `text-message-video-skills` の `text-message-animation/SKILL.md` と必要な `bubble-recipes.md`。`short-form-video` は構成と検品だけ。

**組み立て：** やり取りが始まる → 普通ならこう返すはず、という期待 → 期待と違う返答 → 最後の一言。発言者を台本データで固定し、画面の左右と対応させる。

**画面：** オリジナルのチャット風UIを標準にする。架空の会話という表示を残す。実際のメッセージ画面や本物の証拠に見せかけない。吹き出し・話者名・入力中・既読・最終ツッコミを別レイヤーにする。

**動きと間：** １通ずつ表示する。読める時間を置いて次の返信へ進む。入力中の点々は、返信を待つことに意味がある箇所だけ。最新の文章を自動スクロールし、入力欄や投稿先UIの下に隠さない。送受信音は任意で、無音でも話が通じるようにする。

**使わない：** 全文一括表示、全返信への長い入力待ち、意味のない既読演出。LINE専用の完成テンプレートが同梱されているとは説明しない。

**検品：** 左右と話者が一致するか。返信が順番どおりか。相手の前の発言を見失わないか。最終返信を十分読めるか。改行で意味が変わらないか。

**依頼例：**「『お願い』と言われた途端に渋る場面を会話型に。実在アプリではなく架空チャットUIで。」

<a id="game-ui"></a>
## 3. ゲーム・診断型 — `game-ui`

**選ぶとき：** 選択肢、判定、獲得称号、進捗、能力値など、UIの仕組み自体をボケにするとき。

**読む資料：** この節が主役。補助として [animations](../references/animations.md) と `kinetic-typography`。既成のゲーム動画スキルではなく、このフォーク独自の画面設計。

**組み立て：** 状況 → 選択肢 → 本人の選択 → UI上の結果 → 現実とのズレ。最初に選択前・選択中・結果の３状態を定義する。

**画面：** 同じ場所に選択肢と結果を表示し、視線の移動を減らす。入力していないのにカーソルが勝手に別の選択肢へ飛ぶなど、演出上の因果関係が分からない動きは避ける。数値は必要な場合だけにする。

**動きと間：** カーソルが選択肢へ移動 → 選択状態を短く保持 → 結果を表示。数値カウントやゲージは結果を理解する補助に限る。視聴者が押せる本物のボタンだとは説明しない。

**使わない：** 実測値を装う能力点・割合、根拠のない性格診断、意味のない進捗バー、３Dや派手なゲーム演出の自動追加。実在製品の忠実な再現を目的とするスキルを全体に適用しない。

**検品：** 選択と結果が対応しているか。架空の判定と分かるか。数値を入れた場合、架空の演出値と明示されているか。結果画面でオチを読む時間があるか。

**依頼例：**「旦那が『手伝おうか？と聞く』を選び、『協力した感を獲得。家事は進んでいない』と出るゲーム型に。」

<a id="english-learning"></a>
## 4. 英語クイズ・解説型 — `english-learning`

**選ぶとき：** 英文法、語彙、誤文訂正、２文の違い、短い確認問題。学習内容を理解してもらうことが目的のとき。

**読む資料：** この節。新シリーズの構成整理に限り `remotion-video-director`。クイズに限り `countdown-video`。強調に限り `kinetic-typography`。Remotion資料は英語の正しさの根拠にはしない。

**組み立て（クイズ）：** 問題と必要な文脈を全文表示 → 考える時間 → 答え → 根拠を一つ → 必要なら別例で確認。解説だけならカウントダウンは使わない。

**画面：** 英文を読める位置に保持し、着目語・時間軸・対応関係だけを追加する。日本語解説と英文が互いを隠さないようにする。比較問題は両方の文を同時に見られるようにする。

**動きと間：** カウントダウンは問題文と全選択肢が表示され、入場動作が終わった後に開始する。思考時間とアニメーション時間を混ぜない。答えを出す前に色や効果音で正解を漏らさない。英文の音声がある場合は実際の長さを基準にする。

**使わない：** コメディ用の速い切り替え、理解時間を削る「間なし」ルール、例外のある文法の断定、曖昧な四択の無理な単一正解化。原問題の形式を守る指示があるときは勝手に改変しない。

**検品：** 例文・訳・正解・解説が一致するか。必要な文脈があり、別解の可能性を確認したか。資料にない文法を追加したときは検証したか。思考時間が実際に確保されているか。生徒名・成績・学校内資料などを公開リポジトリに入れていないか。

**依頼例：**「現在完了と過去形の違いを解説型で。英語学習モードを使い、比較する２文を消さずに見せて。」

<a id="app-promo"></a>
## 5. アプリ紹介型 — `app-promo`

**選ぶとき：** 実在する自作アプリの紹介、操作説明、使いどころの提案。視聴者に利用の具体像を持ってもらいたいとき。

**読む資料：** この節 → [ad-copywriting](../references/ad-copywriting.md)。画面の見せ方は [website-videos](../references/website-videos.md) の必要箇所、実UIの忠実性や検品は `remotion-motion-graphics-skill` の必要箇所だけ。

**組み立て：** 具体的な困りごと → 実画面で１操作 → 起こる結果 → 利用場面。行動案内は必要なら最後に１つだけ。新機能を足すのではなく、今できることを見せる。

**画面：** ユーザー提供または閲覧許可を得た実画面を使う。何を押したかと何が変わったかを同じ流れで見せる。見やすさのための拡大はよいが、存在しないボタン・機能・利用者数を作らない。

**動きと間：** 操作する箇所を示す → 操作 → 結果を読む。目立つ画面切り替えのために操作の因果関係を省かない。画面録画に文字の説明を重ねるときは重要UIを避ける。

**使わない：** 存在しない実績・レビュー・値引き・機能、資料だけを根拠にした最新価格の断定。実画面がないときは「説明用モック」と明記するか、画面に依存しない台本案に留める。

**検品：** 紹介した機能が実際に存在するか。実在アプリのURL・名称・価格を必要に応じて確認したか。画面の個人情報が隠れているか。操作を再現できるか。公開・広告出稿・課金は別途ユーザーの依頼があるか。

**依頼例：**「このアプリの『迷ったときの１回の操作』だけを紹介。実画面を使い、存在しない機能や実績は追加しないで。」
